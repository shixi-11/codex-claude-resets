## October 24 collection gap investigation

Run [40067829074](https://github.com/shixi-11/codex-claude-resets/actions/runs/40067829074) was created and started at 05:50:27 UTC. Its predecessor [40046083523](https://github.com/shixi-11/codex-claude-resets/actions/runs/40046083523) was created and started at 00:39:54 UTC. The repository Actions run history contains no intervening run: this was a gap in scheduled run creation, not a five-hour collector execution or runner queue. The hourly minute-17 schedule, daily digest, manual trigger and concurrency settings were present. The available public API does not establish GitHub's internal reason for the missed/delayed triggers. GitHub [documents that schedule events can be delayed and queued jobs may be dropped](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); this limitation is consistent with the history, not proof of a particular service incident.

The preceding committed audit was `2026-10-24T00:40:35.173Z`; the next was `2026-10-24T05:51:08.541Z`, a gap of 18,633,368 ms (5 h 10 m 33.368 s). Both 114-test runs, the fresh collection and the nine-language build passed in the latter run. Its final collection-gap alert correctly failed the job after records were saved. The three-hour threshold, source health checks and alert step remain unchanged. Audit artifacts now retain `gapMs` and `previousCheckedAt` so this distinction is inspectable. A regression reproduces the exact gap even with healthy current sources. No repository-only change can guarantee that GitHub creates scheduled jobs; an independent scheduler would require separate infrastructure configuration, which is outside this repair.

The production workflow is `.github/workflows/site.yml`. It requests announcement checks at minutes 17 and 47 UTC each hour, writes a daily Markdown digest at 02:23 UTC, validates records and the static build, then commits changed records to this public repository. Vercel's GitHub integration receives those commits and builds `dist/` with `node scripts/build.mjs`. No GitHub Pages environment or Vercel credential in Actions is required.

The Vercel project is `codex-claude-resets` in the existing `shixilin` workspace, with production origin `https://codex-claude-resets.vercel.app/`. Only the built `dist/` directory is served; collector scripts and Blender sources are not included in it. Vercel Standard Protection keeps previews and generated deployment URLs protected while the production alias remains public. The personal website routes `shixilin.com/ai/codex-claude-resets/` to this Vercel project. Project-level routing permits this origin change without redeploying unrelated work on the main website; the main site's `vercel.json` must retain the matching Vercel origin for future deployments.

Standard GitHub-hosted runners on this public repository do not consume the owner's private Actions minutes. Other private repositories on the account still share the GitHub Free 2,000-minute allowance. This project does not enable a paid budget. Vercel deployment success and Actions collection success are separate checks: verify a bot-authored record commit produces a ready production deployment and that its `health.json` reaches the public URL.

The default collector needs no token, LLM or billing account. Tibo and ClaudeDevs public timelines are polled through FxEmbed. Community discovery pages supply fallback URLs only. X official embeds verify the author, post identity and visible text. Full long-post text can be retrieved through FxEmbed after the author, ID, timestamp and visible official excerpt match; provenance identifies that relay. Full source text is hashed, not republished in full. Quotes are limited to a short excerpt.

`X_BEARER_TOKEN` together with `ENABLE_PAID_X_API=true` explicitly selects the optional official timeline adapter when running the collector. The hosted workflow does not set either value. Operators must review X's current pricing and permissions before enabling this path. There is no silent paid fallback.

Optional human editorial work can use a locally authorized Grok subscription CLI, model `grok-4.6`, reasoning `high`, for editorial review of supplied public evidence. The installed Research session tested on September 8 could not live-search X, so it is not used as a timeline collector. A code or chronology review can use the operator's available Codex model at `medium` or `high` reasoning. This is an editorial choice, not a cron dependency. Keep OAuth, local profiles and subscription credentials off GitHub runners. Model output is advisory and must link to a primary source.

Failed discovery or verification retains existing event records. The health file records the current attempt and source failures. The browser also ages the timestamp so a failed deployment cannot leave a permanently green status. A daily digest with no collected posts says exactly that; it does not claim no reset happened.

GitHub scheduled workflows have no real-time guarantee and can be disabled after prolonged repository inactivity. Review the Actions page and the site's visible last-check time. `workflow_dispatch` allows an operator to run a fresh check. Site consumers can use RSS or JSON; the workflow does not publish to social accounts or message third parties.

## November 11 repeated-gap alert repair

The public run history contains schedule runs [42879580795](https://github.com/shixi-11/codex-claude-resets/actions/runs/42879580795) at November 10 18:52:30 UTC, [42928083076](https://github.com/shixi-11/codex-claude-resets/actions/runs/42928083076) at November 11 00:01:46 UTC, and [42970353531](https://github.com/shixi-11/codex-claude-resets/actions/runs/42970353531) at 06:08:37 UTC. The successive creation gaps were 5 h 9 m 16 s and 6 h 6 m 51 s. Each run started at its creation timestamp and completed in about two minutes; no intervening created run or long-running publish lock explains these gaps. The two hourly opportunities and ten-minute timeout were already present. GitHub documents possible delayed/dropped schedule events; public evidence does not establish its internal cause, and changing the cron expression would not provide an independent scheduling guarantee.

The 06:08 run successfully checked all six sources and published commit `76875a0500d61c98be502fbdcaede105fbe68d7e`. The public `health.json` was independently observed with both platforms successful at `2026-11-11T06:09:14.059Z`. That recovery does not erase the earlier gap. Job `130357141290` nevertheless recorded `status: attention`, `newAlerts: 0`, then skipped its final alert step: the persistent `collection-gap` key from the preceding run suppressed the new interval. The committed audit timestamps were `2026-11-11T00:03:45.738Z` and `2026-11-11T06:10:35.305Z`, 22,009,567 ms apart.

Each interval exceeding three hours now produces a new gap alert, even when the preceding interval also exceeded three hours. Unchanged source failures and review records still deduplicate, and a subsequent timely audit clears the gap. The threshold, source checks, publish-before-alert order, schedule, concurrency and frontend remain unchanged. Regression tests reproduce the committed audit timestamps, persisted state shape, consecutive gaps, timely recovery, exact three-hour boundary and unchanged review deduplication. This fixes misleading successful workflow status; it does not fix GitHub's missing trigger creation.

A genuine fallback requires an independently authorized clock and narrowly scoped ability to dispatch this workflow. It should check recent attempts, skip queued/in-progress refreshes, and dispatch once when the last attempt is older than two hours. It must not rewrite health timestamps or weaken source validation. No external scheduler, credential or permission expansion is introduced by this repair.
